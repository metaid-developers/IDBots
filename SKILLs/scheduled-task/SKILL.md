# 定时任务 Skill

## 使用场景

当用户想要：
- 设置定时执行的任务（每天、每周、每月、自定义 Cron）
- 创建一次性定时执行的任务
- 安排定时自动化检查、报告生成、代码备份等
- 设置定期监控或提醒

## 创建定时任务

### Step 1: 收集信息

先与用户确认以下信息（如果用户未提供）：
1. **任务名称**（必填）— 简短描述
2. **执行内容**（必填）— 任务运行时 Claude 收到的 prompt 指令
3. **执行频率**（必填）— 一次性、每天、每周、每月或自定义 Cron
4. **工作目录**（可选）— 默认为当前会话的工作目录
5. **通知平台**（可选）— 任务完成后发送通知
6. **会话绑定**（可选）— 默认规则：一次性任务（`schedule.type` 为 `"at"`）绑定当前会话，重复任务（`interval` / `cron`）每次新建会话。承接当前工作的后续/检查类任务建议显式传 `"sessionId": "current"`；也可传指定会话的 UUID；一次性任务想避开默认绑定时传 `"sessionId": null`

### Step 2: 构建 JSON 并执行脚本

#### Schedule 类型

**一次性执行（at）：**
```json
{ "type": "at", "datetime": "2026-03-15T09:00:00" }
```

**Cron 表达式（cron）— 5 字段格式：分 时 日 月 周**
```json
{ "type": "cron", "expression": "0 9 * * *" }
```

常用 Cron 示例：
| 表达式 | 含义 |
|--------|------|
| `0 9 * * *` | 每天 9:00 |
| `0 8 * * 1` | 每周一 8:00 |
| `0 9 * * 1-5` | 工作日 9:00 |
| `0 0 1 * *` | 每月1号 0:00 |
| `*/30 * * * *` | 每30分钟 |
| `0 * * * *` | 每小时整点 |
| `0 9,18 * * *` | 每天 9:00 和 18:00 |

#### 执行脚本创建任务（推荐：`@file` 方式，避免 Windows 中文编码问题）

当 payload 含中文时，**不要**把整段 JSON 直接作为命令行参数传入。  
请先写入 UTF-8 文件，再用 `@文件路径` 传给脚本。

```bash
# "sessionId": "current" 表示在「当前会话」中运行；删除该行则每次都在新会话中运行
# 注意：interval / cron 类重复任务必须带 "exitCondition"（见下方「周期任务退出机制」）
cat > /tmp/scheduled-task.json <<'JSON'
{
  "name": "任务名称",
  "schedule": { "type": "cron", "expression": "0 9 * * *" },
  "prompt": "任务运行时 Claude 将执行的详细指令...",
  "workingDirectory": "/path/to/project",
  "sessionId": "current",
  "exitCondition": "端点确认可用且工单 xxx 交付后停用本任务；若工单已关闭，下次触发即停用",
  "maxFires": 50
}
JSON

bash "$SKILLS_ROOT/scheduled-task/scripts/create-task.sh" @/tmp/scheduled-task.json
```

#### 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | ✅ | 简短的任务名称 |
| `prompt` | ✅ | 任务运行时执行 agent 收到的指令（应清晰完整） |
| `schedule` | ✅ | 调度配置（见上方类型说明） |
| `workingDirectory` | ❌ | 执行目录（默认空） |
| `sessionId` | ❌ | 任务每次执行所在的会话。默认值规则：一次性任务（`schedule.type` 为 `"at"`）在会话中创建时默认绑定当前会话；重复任务（`interval` / `cron`）默认每次新建会话。显式传 `"sessionId": null` 可为一次性任务选择新会话。显式传 `"current"` = 当前所在会话（**推荐**在检查刚设置好的发版、构建或部署等承接当前工作的场景显式传入）；其他字符串 = 该会话的 UUID。绑定的会话在运行时已不存在或已归档时，任务会自动退回新会话运行（此时响应中会带上顶层字段 `sessionWarning`）。更新任务时：省略该字段 = 保持原有绑定，传 `null`（或 `""`）= 清除绑定 |
| `metabotId` | ❌ | 定时会话所属 MetaBot 的数字 id（默认 null = Twin/默认会话身份）。传入后任务将以该 bot 的身份运行：会话归属该 bot，且未显式指定 `workingDirectory` 时自动使用该 bot 的专属工作目录。适合「让某个 Worker bot 每天以本人身份跑自己的活」的场景（如新员工入职首跑、每日简报）。bot id 可通过 metabot_list / My Bots 查看 |
| `description` | ❌ | 详细描述（默认空） |
| `systemPrompt` | ❌ | 自定义系统提示词（默认空） |
| `executionMode` | ❌ | `"auto"` / `"local"` / `"sandbox"`（默认 `"local"`） |
| `expiresAt` | ❌ | 过期日期 `"YYYY-MM-DD"`（默认 null，不过期） |
| `exitCondition` | 重复任务✅ | **退出条件**（自然语言）：何时使命完成、应自行停用。必须同时覆盖①探测的信号本身成立，②它所服务的上游事项（工单/帖子/群任务）已经收口或不再需要。一次性 `at` 任务不需要。缺失时创建会被拒绝并返回示例 |
| `maxFires` | ❌ | 触发次数上限（正整数）。通过脚本/API 创建的重复任务缺省 **50 次**：到达后任务自动停用（`lastStatus=max_fires_reached`）。长期例行任务可显式调高 |
| `origin` / `originSessionId` / `originContext` | — | 只读：宿主自动记录的创建来源（人工 UI / bot 会话 / a2a / 群任务等），创建后不可修改 |
| `notifyPlatforms` | ❌ | 通知平台数组：`["dingtalk","feishu","telegram","discord"]`（默认 `[]`） |
| `enabled` | ❌ | 是否立即启用（默认 `true`） |

### Step 3: 确认结果

脚本返回 JSON 响应：
- 成功：`{ "success": true, "task": { "id": "...", "name": "...", ... } }`
- 失败：`{ "success": false, "error": "错误信息" }`

向用户确认以下信息：
- ✅ 任务名称和 ID
- ⏰ 执行频率（人类可读格式，如"每天早上 9:00"）
- 📋 执行内容摘要
- 💡 提示用户可在「设置 → 定时任务」中管理

## 周期任务退出机制（必读）

周期任务（`interval` / `cron`）只有出生证明、没有死亡条款，就会变成永久的噪音（真实事故：一个端点探测任务在它服务的工单早已交付后，又每 2 小时跑了 4 天共 61 次）。因此：

1. **创建即带死亡条款**：`exitCondition` 对重复任务是必填的（缺失会被 API 拒绝）。写法要覆盖两种死亡：
   - **条件型**：探测的信号本身触发了（如「端点由不可用变为在线」）——任务下一轮自己就能看见；
   - **生命周期型**：看它的理由消失了（上游工单已交付、帖子已回复、群任务已收口）——信号面上什么都不会发生，只有执行任务的你判断得出来。**条款里必须点名上游事项**，例：「端点确认可用且工单 order-x 交付后停用本任务；若工单已关闭，下次触发即停用」。
2. **每次触发时判断退出**：宿主会在任务 prompt 前注入 `[Scheduled task lifecycle]` 块（第几次触发 / 预算余量 / 退出条件原文 / 创建来源会话）。**每次执行完主体工作后，对照条款判断：条件已满足或存在理由已消失，就当场停用自己**——`bash "$SKILLS_ROOT/scheduled-task/scripts/toggle-task.sh" <task_id> false`（task id 在注入块里），并在收尾说明中写明已停用及原因。把一个使命已尽的任务留着继续跑是缺陷，不是谨慎。
3. **预算兜底**：重复任务缺省 50 次触发上限（`maxFires`）。最后一发前宿主会预告「这是最后一次触发」。到达上限任务自动停用，`lastStatus=max_fires_reached`。
4. **续期必须显式**：重新启用一个已停用的任务 = 显式续期，触发计数从零开始；也可以用 `update-task.sh` 修改 `exitCondition` / `maxFires`（创建来源字段不可改）。

## 收尾跟进声明（必读）

每次运行结束，**最后一条消息必须以恰好一行标签收尾**（宿主会把这一行注入到每次任务的 prompt 前作为契约；创建任务时也应把该要求写进 `prompt`）：

- `[FOLLOW_UP: none]` — 本次运行没有任何事需要主人决策、批准、出钱或回复：工作已闭环、下一步是你自己继续、或在等另一个 bot / 第三方 / 群（那是他们的跟进，不是主人的）。
- `[FOLLOW_UP: owner — <一句话：主人需要决策/批准/提供什么>]` — 仅当**主人本人**必须行动，工作才能继续时使用。

规则：

- **不许省略标签**。标签决定会话进入主人的「待跟进」区还是留在自主任务区——漏标或错标都会消耗主人没有欠的注意力。
- **第三方的事不要标 `owner`**：风险处置权在导演/制片方/其他 bot、等某个外部的人回复、群任务等别人交件——这些一律标 `none`，由你按自己的节奏跟进。
- **条件式提议不是提问**：「如果你愿意，我也可以顺手…」属于信息性收尾，标 `none`。
- 标签单独成行，放在消息最后；正文里其余内容不受影响。

## 重要注意事项

- **编码安全（Windows 必看）**：含中文 payload 必须优先使用 `@file` 方式，避免命令行参数编码导致标题/提示词乱码
- **相对时间（Windows 必看）**：当用户说“X 分钟后 / 明早 9 点 / 今天下午”等相对时间时，先用本机命令获取当前本地时间，再换算目标时间。不要直接猜测当前时间，也不要使用 UTC 时间。
- **创建顺序（防过期）**：当用户要求“1 分钟后/5 分钟后”等短延时一次性任务时，先立即创建定时任务，再进行任何耗时操作；不要先联网检索、总结内容再创建任务。
- **Prompt 边界**：`prompt` 应描述“任务触发时要执行的动作”，不要提前执行任务并把静态结果写进 prompt。示例：写“到点后检索昨天 AI 新闻并发送摘要”，不要先把新闻列表整理好再塞进 prompt。
- 推荐命令（跨平台）：
  ```bash
  node -e 'const d=new Date();const p=n=>String(n).padStart(2,"0");console.log(`${d.getFullYear()}-${p(d.getMonth()+1)}-${p(d.getDate())}T${p(d.getHours())}:${p(d.getMinutes())}:${p(d.getSeconds())}`)'
  ```
- **自动执行**：定时任务运行时所有工具调用自动批准（auto-approve），无需人工审批
- **独立运行**：`prompt` 是任务独立运行时执行 agent 收到的唯一指令，应写得清晰完整
- **自动禁用**：连续失败 5 次的任务会自动禁用；重复任务另有触发次数预算（`maxFires`，脚本/API 创建缺省 50 次），到达上限自动停用（`max_fires_reached`）
- **一次性任务**：`type: "at"` 的任务执行后自动禁用
- **Cowork 会话**：每次执行会创建一个新的 Cowork 会话（标题前缀为「[定时]」），可在 Cowork 列表中查看执行详情
- **会话绑定**：绑定后 prompt 会直接注入指定会话，执行记录以普通对话轮次出现在该会话中（而不是新建「[定时]」会话）。一次性任务默认绑定创建它的会话，重复任务默认每次新建会话；显式传 `sessionId` 可覆盖，一次性任务也可以传 `"sessionId": null` 回到新会话。绑定的会话在运行时已不存在、已归档，或为 A2A / 沙箱会话时，任务会自动退回新会话运行。
